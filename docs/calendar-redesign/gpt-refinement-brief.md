# GPT 视觉母版：受控精修提示词

> 用途：把已经选定的 GPT 概念作为唯一视觉母版，交给两个不同模型做一次受控精修。
>
> 这不是新一轮自由设计，也不是前端实现任务。两个模型必须使用同一份提示词、同一组参考材料和同一组功能事实，最后只比较它们对指定问题的解决质量。

## 使用方法

1. 为两个模型分别开新会话。
2. 将下方“完整提示词”原样复制给两个模型。
3. 只替换以下两个变量：
   - `{{MODEL_ID}}`：例如 `refinement-opus-01`、`refinement-qwen-01`。
   - `{{OUTPUT_DIR}}`：例如 `docs/calendar-redesign/candidates/refinement-opus-01/`。
4. 给两个模型提供完全相同的参考文件：
   - `docs/calendar-redesign/candidates/candidate-GPT-01/CONCEPT-V3-GPT.md`
   - `docs/calendar-redesign/candidates/candidate-GPT-01/concept-v3-GPT/01-neutral-month-GPT.png`
   - `docs/calendar-redesign/candidates/candidate-GPT-01/concept-v3-GPT/02-sumeru-filter-GPT.png`
   - `docs/calendar-redesign/candidates/candidate-GPT-01/concept-v3-GPT/03-character-detail-GPT.png`
   - `docs/calendar-redesign/candidates/candidate-GPT-01/concept-v3-GPT/04-mobile-orbit-GPT.png`
   - `docs/calendar-redesign/multi-model-design-brief.md` 的产品事实和功能契约部分
5. 如模型可以读取项目文件，让它只阅读提示词列出的功能事实文件，不要把现有 CSS 和 DOM 当作视觉参考。
6. 两个模型都只提交概念图和说明，不修改 `src/`，不实现完整 React，不运行长时间的调试流程。

> 重要：不要给一个模型额外的审美参考图，也不要给另一个模型额外的工程上下文。否则这次比较会失去意义。

8. 移动端保留“主角舞台 → 月历 → 下一事件/详情”的纵向节奏，不要把桌面端左右栏简单压缩成拥挤的卡片。
9. 设计要依靠比例、留白、字级、图像裁切和网格成立；不能依赖满屏粒子、持续动画或大量发光效果。

以下内容不是不变量，可以修改：

- 顶部英文品牌和副标题。
- 具体按钮文字、图标和控件分组。
- 月历事件的头像密度和排布机制。
- 控件展开后的面板结构。
- 阵营色的具体色值，但不能破坏整体中性底。
- 角色详情中的信息排序。

==================================================
三、本轮必须解决的五个问题
==================================================

问题 A：功能较多，但不能破坏 GPT 的构图

现有功能包括：

- 上一个 / 下一个月或周、回到今天。
- 月视图 / 周视图。
- 生日 / 首次实装日期模式。
- 四个游戏的多选。
- 游戏对应的属性、稀有度、武器 / 命途 / 特性、地区 / 阵营 / 组织筛选。
- 搜索角色并定位月份。
- 只看收藏、收藏数量。
- 添加和编辑角色。
- JSON 导入、JSON 导出、ICS 导出。
- 更新角色数据、显示更新状态和最后更新时间。
- 周起始日、显示密度、立绘背景、动态效果、主题跟随等偏好。

不要把这些功能全部放在顶部，也不要让它们拥有同等视觉权重。请设计一个分层方案：

常驻核心控制建议包含：

- 上一月 / 下一月。
- 今天。
- 月 / 周。
- 生日 / 实装。
- 当前筛选摘要。
- 搜索入口。

低频或次级控制建议进入一个统一的可展开入口，例如“筛选 / 显示 / 更多”，展开后在同一块面板内分组，不要制造许多互相重叠的浮层。添加、导入、导出、同步、偏好可以放在“更多”或设置面板中。

你可以采用点击后展开的控制面板，但必须说明：

- 面板从哪里展开。
- 展开后不会遮挡哪些核心信息。
- 点击外部、完成或 Escape 如何收起。
- 当前筛选状态在面板关闭后如何被看见。

问题 B：建立三档头像密度规则

月历中必须明确展示以下三种情况，且不能让每个日期都变成海报：

1. 当天只有 1 个角色：使用 Opus 方案启发的较大角色头像 / 肖像作为日期格主角。桌面端建议约 48–64px，但必须受日历行高限制；日期数字位置保持稳定，头像不能把网格撑高。头像下方或邻近位置保留角色名或足够的识别线索。
2. 当天有 2–3 个角色：使用紧凑的头像堆叠。头像可重叠约 25–35%，全部角色应能看出；不要再叠加大量文字。必要时保留主要角色名或数量提示。
3. 当天有 4 个及以上角色：使用小头像横排或“头像 + 短横条”。最多显示 3–4 个头像，末尾显示“+N”；“+N”必须是当天完整名单的入口，不能静默丢失角色。

移动端统一缩小为：

- 1 个角色：约 30–40px。
- 2–3 个角色：约 24–30px 堆叠。
- 4 个及以上：约 18–24px 小头像 + “+N”。

请在概念图中用真实角色素材或清晰标注的代表素材展示这三种密度。日期数字、星期标题、今天状态、选中状态的位置要稳定。游戏 / 地区颜色只用于头像环、底部细线、事件点或小面积强调，不要给每个日期格涂一块不同颜色。

问题 C：让游戏 / 地区 / 阵营产生可感知但不喧宾夺主的变化

用户点击不同游戏或地区 / 阵营的角色时，允许出现以下变化：

- 左侧主角立绘或主角选择。
- 舞台光晕和一处主强调色。
- 小型标签、头像环、事件点或细线。
- 与该上下文相关的简短中文名称或 tagline。

不能出现以下变化：

- 整个应用更换成另一套完全不同的布局。
- 每个日期格都有不同材质或颜色。
- 需要依赖动画才能理解的变化。
- 虚构星穹铁道或崩坏3目前项目中不存在的细分阵营。

至少在一张图中展示“原神 / 须弥”或其他真实已支持的地区上下文；同时说明如果只选择游戏而没有细分地区时如何回落到游戏级主题。

问题 D：处理 GPT 方案中不明确的文字

不要继续使用会让用户以为存在额外产品功能的“INSIGHTS”。当前产品没有数据洞察、统计分析或报告页。

“LUMEN / CHARACTER ORBIT”不能作为虚构的导航功能。你可以选择以下一种处理方式，并在说明中明确理由：

1. 删除 LUMEN，仅使用清晰的中文产品标题，例如“米哈游角色生日日历”或“角色生日与实装纪念日”。
2. 保留 LUMEN 作为非常小的品牌代号，旁边必须有清晰的中文产品名称，不能让它承担功能导航。
3. 将其改成不制造虚构功能的短副标题，例如“角色生日与实装纪念日”。

顶部导航只能表示真实存在的范围或设置。不要发明 Collection、Insights、Orbit、Memory Index 等新页面。如果保留英文，它们只能是品牌或视觉小标签，不能暗示不存在的功能。

问题 E：移动端必须保留主视觉和可用性

移动端不是桌面端的缩小截图。请保留：

- 一个明确但不过大的主角图像区域。
- 可读的月份和翻页 / 今天操作。
- 7 列月历或等价的可快速扫描月视图，不要改成长横向滚动海报。
- 头像密度规则的移动版。
- 一个清晰的筛选入口；展开后使用底部抽屉或不遮挡核心状态的面板。
- 点击日期或角色后可以进入详情，并有明确返回路径。

移动端顶部不要堆放所有功能；搜索、筛选、更多操作可以使用图标按钮或统一入口，但图标必须能从上下文理解，必要时提供短标签。

## 两个模型的比较方式

两个模型必须使用同一份提示词。不要根据模型名称预先指定“一个负责审美、一个负责功能”，否则会造成比较偏差。

完成后只做以下比较：

| 维度 | 观察重点 | 权重 |
|---|---|---:|
| 母版保真度 | 是否仍然一眼是 GPT 方案 | 25 |
| 月历可读性 | 日期、今天、事件密度是否清楚 | 25 |
| 控件收纳 | 功能是否完整但不破坏构图 | 20 |
| 头像密度 | 1 / 2–3 / 4+ 三档是否自然 | 15 |
| 移动端 | 是否保留舞台感并可扫描 | 10 |
| 实现可信度 | 后续是否能落到 React / CSS | 5 |

不要把两份结果拼成第三套设计。最终只保留 GPT 母版，并从胜出的精修稿中选择少量明确机制，例如：

- 一种更好的展开式控制面板；
- 一套更稳定的头像堆叠规则；
- 一个更清楚的中文标题和筛选摘要；
- 一个更成熟的移动端筛选入口。

如果两个精修稿都没有比 GPT 母版更好，停止继续跑模型，直接冻结视觉方向并进入正式实现规划。
