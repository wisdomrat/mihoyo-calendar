# 日历视觉概念阶段 V3：审美优先的概念提案任务书

> 用途：在正式前端实现之前，先确定一个真正值得实现的视觉方向。  
> 本轮只产出概念图和简短视觉说明，不写生产代码，不做完整交互原型，不调试响应式细节。  
> 建议交给多个前端/视觉能力最强的模型分别执行，再进行匿名视觉评审。  
> `candidate-01`、`candidate-02`、`candidate-04` 的长篇工程型方案保留为历史实验，不作为本轮视觉模板。

## 0. 本轮任务的改变

之前的候选任务把“功能完整、响应式、组件边界、数据契约、原型交互、截图验证”全部塞进同一轮，模型自然会把主要精力用在证明方案可实现，最后得到概念合理但画面普通的页面。

本轮采用两阶段流程：

1. **概念阶段（现在）**：只判断视觉方向是否漂亮、独特、适合角色日历，并能覆盖核心场景。
2. **实现阶段（之后）**：选定一个方向后，再把功能契约和前端实现约束交给模型。

概念阶段的成功标准不是“功能覆盖 100%”，而是：

- 截图第一眼有明确视觉主张。
- 角色图片、日期和游戏/阵营气质形成一个有记忆点的整体。
- 画面有高级感、层次、节奏和留白，而不是模板化的控件堆叠。
- 方向在真实实现时不会立即与日历核心任务冲突。

## 1. 给模型的事实范围

这是一个米哈游角色生日/首次实装纪念日日历。用户主要做三件事：

1. 扫描一个月哪些日期有角色事件。
2. 点击角色查看名字、游戏、日期、属性、地区/阵营和立绘。
3. 在原神、星穹铁道、绝区零、崩坏3之间筛选，并感受不同游戏/地区/阵营的气质。

附加能力（本轮不必全部画出）：搜索、收藏、生日/实装切换、月/周切换、添加/编辑角色、JSON/ICS 导入导出、数据同步。

视觉需要支持的核心场景只有三个：

- 中性状态的月视图。
- 选中一个游戏/地区/阵营后的月视图。
- 点击角色后的详情/立绘状态。

目前已有归属信息：

- 原神有蒙德、璃月、稻妻、须弥、枫丹、纳塔、至冬等地区。
- 绝区零有狡兔屋、维多利亚家政、白祇重工等阵营。
- 星穹铁道和崩坏3目前只有游戏级 fallback，不能虚构更细阵营。

## 2. 重要的去锚定规则

### 2.1 禁止读取

概念完成前，不要读取：

- `src/App.tsx`
- `src/components/**`
- `src/index.css`
- `src/styles/theme.css`
- `src/components/Hero.css`
- `dist/**`
- 现有网站截图、录屏或浏览器页面
- `docs/calendar-redesign/candidates/**`
- V1/V2 任务书中的旧结构指纹、旧方案和旧截图

现有页面只作为项目背景，不作为视觉参考。不要在旧页面上“改得更好看”。

### 2.2 这轮明确不要重复的方向

为了避免前两轮的收敛，本轮不要把下面这些作为主概念：

- 纸张、年鉴、档案、长卷、书脊、装订条。
- “无边界月历 + 底部命令坞”。
- 大面积米白纸面配细灰网格。
- 黑色左侧窄轨配红色竖线。
- 通过水印字、点阵、邮票、票据的组合制造“档案感”。
- 典型 SaaS Dashboard：顶部标题 + 左筛选 + 右侧卡片网格。

这不是禁止使用某个单独元素，而是禁止再次把上述整套隐喻或结构作为核心答案。

### 2.3 允许大胆，但要有审美控制

可以使用玻璃、霓虹、渐变、摄影式裁切、非对称构图、强烈字体、局部 3D、粒子、游戏 HUD、杂志排版、舞台灯光、色块、插画式背景等。

但每种强烈手法都必须满足：

- 有明确的产品语义或游戏语义。
- 有边界，不在每个组件上重复。
- 有主次，不让装饰抢走日期和角色。
- 即使移除动效，静态截图仍然成立。

## 3. 概念模型提示词

下面整段可以直接交给候选模型。每个模型使用新会话，并替换 `{{CANDIDATE_ID}}` 和 `{{CREATIVE_LENS}}`。

```text
你是 {{CANDIDATE_ID}}，本轮担任视觉总监、品牌设计师、产品 UI 艺术指导和游戏内容设计师。

项目：米哈游角色生日/首次实装纪念日日历
项目目录：D:\work\coding\mihoyo-calendar
本轮唯一目标：提出一个值得正式实现的、高审美的日历工作区视觉概念。

创意透镜：{{CREATIVE_LENS}}

你现在不是前端开发者，也不是测试工程师。不要修改生产代码，不要搭建完整交互原型，不要为所有功能写组件映射，不要运行构建和测试，不要花大量时间调试 CSS。你只需要做足够接近最终视觉的概念图，用来判断方向。

严格遵守以下规则：

1. 概念完成前不要读取现有 UI、组件、CSS、旧截图、V1/V2 任务书或其他候选。现有页面不能成为你的布局参考。
2. 只使用本提示词中的产品事实。若需要角色图片，可以读取角色 JSON 和已有图片资源，但不必扫描整个项目。
3. 不要设计纸张、年鉴、档案、长卷、书脊、装订条或“无边界月历+底部命令坞”方向；前两轮已经验证这些方向概念完整但审美不够好。
4. 不要把“功能完整”误认为“设计完成”。本轮优先判断构图、比例、材质、字体、角色内容、色彩关系和整体气质。
5. 不要输出冗长的工程论文。最多 1200 字说明，核心证据必须在概念图里。

一、先做视觉发散，但不要把五个方案都做成完整页面

在内部快速比较至少四种不同的艺术方向。每个方向只需写：
- 一句话视觉主张。
- 主要视觉媒介（例如光、摄影式裁切、动态图形、品牌海报、空间界面、游戏 HUD 等）。
- 最大审美风险。

然后选择一个最终方向。最终方向不得是“在现有日历上换色、换圆角、加背景纹理”。

二、最终概念必须先回答四个审美问题

1. 用户打开页面的前三秒，眼睛先看哪里、第二看哪里、第三看哪里？
2. 为什么这个页面一眼能被识别为“米哈游角色日历”，而不是普通日历或 SaaS Dashboard？
3. 角色立绘/头像、日期信息、游戏/阵营氛围分别占多少视觉权重？为什么？
4. 如果去掉所有动画和大部分颜色，这个设计靠什么仍然成立？

三、必须交付四张概念图，不要做完整产品

概念图只需要覆盖关键视觉，不需要真实可操作：

1. 1440×900：中性状态月视图，作为主视觉母版。
2. 1440×900：选中一个原神地区或绝区零阵营后的状态，展示上下文变化。
3. 1440×900：角色详情/立绘状态，展示内容层级和角色表现力。
4. 390×844：移动端主视觉或详情状态，证明不是只适合桌面。

如果无法制作真实截图，可以制作高保真静态 HTML/SVG/PNG 概念板；不要搭建完整交互，不要制作十几张状态截图。四张图比几十张半成品更重要。

概念图要求：

- 至少使用 2-4 个真实角色头像/立绘，或明确标注的同风格代表素材。
- 使用真实中文角色名和游戏名，避免 lorem ipsum。
- 画面中只放足够说明结构的控件，不要把所有设置按钮都堆上去。
- 允许隐藏低频功能，只要不改变整体视觉判断。
- 不要在图中出现“原型”“demo”“上下文演示”“TODO”“候选编号”等调试文字。
- 不要让占位色块、默认浏览器控件或未处理的图片破坏概念判断。

四、视觉规范说明（简短即可）

在概念图之后，用简短条目说明：

- 一句话设计主张。
- 创意透镜如何转化为界面语言。
- 版式骨架和视觉焦点。
- 字体选择与字号层级。
- 主色、辅助色、中性色和阵营色如何分工。
- 角色图片的裁切、比例和出现位置。
- 月视图中“有事件/今天/选中/多角色”的视觉表达。
- 选中不同游戏或阵营时，哪些设计改变、哪些必须稳定。
- 哪些区域使用玻璃、霓虹、渐变、纹理或动效，以及为什么。
- 这个方向最可能失败的地方。

五、不要在本轮做的事

- 不要写 React/TypeScript 组件。
- 不要复制现有 CSS token、类名或布局。
- 不要实现筛选、搜索、ICS、JSON、同步等完整逻辑。
- 不要为了证明响应式而调试 360px 的每一个像素。
- 不要写完整的迁移计划、测试计划或组件树。
- 不要把大量文字说明当成视觉质量证明。

六、自评门槛

提交前请用下面标准审查自己的四张图：

- 视觉主张清晰度：20 分。
- 构图、比例、留白和视觉层级：25 分。
- 米哈游角色/IP 内容表现力：20 分。
- 颜色、字体、材质和组件的一致性：15 分。
- 与前两轮方向的差异和记忆点：10 分。
- 日历作为工具仍然可信：10 分。

如果总分低于 75，先重做主视觉，不要继续补写说明。
如果四张图看起来像四个不同产品，先统一视觉系统。
如果画面只是漂亮背景+普通日历，判定为失败。

最终文件：
```

## 4. 建议分配给不同候选的创意透镜

为了减少模型之间再次收敛到同一个“抽象好听但画面普通”的答案，建议不要让所有模型使用完全相同的创意起点。

| 候选 | `{{CREATIVE_LENS}}` | 设计提醒 |
|---|---|---|
| candidate-05 | 高级游戏角色收藏界面 / premium character collection | 重点是角色内容、收藏欲和精致排版；不要做卡牌手游 UI。
| candidate-06 | 米哈游世界观地图与现代导航的结合 | 重点是空间、区域、路线和归属感；不要做纸质地图或年鉴。
| candidate-07 | 时尚杂志与游戏主视觉的结合 | 重点是编辑性构图、图片裁切和字体；不要做海报拼贴到无法使用。
| candidate-08 | 具有游戏感的动态舞台，但静态截图也成立 | 重点是层次、光线和状态变化；不要使用持续粒子或赛博模板。

创意透镜不是让模型照抄某一种现成产品，而是逼它从不同的艺术起点构思。最终评审仍然只看图，不看模型名称。

概念图完成后，把匿名候选图和简短说明交给独立评审模型。不要把候选的工程文档、模型名称或生成过程交给评审。

## 6. 组织者的执行建议

- 让每个候选只花有限时间做四张概念图，不要让它们进入完整原型开发。
- 候选可以使用真实角色素材，但不必实现真实数据、筛选或导航。
- 不要在概念阶段要求 10 个视口、20 个状态或自动化测试。
- 评审时优先看图，再看说明；说明不能替代画面。
- 如果候选都“有想法但不好看”，下一轮应修改创意透镜或提供 2-3 张高质量参考图，而不是继续增加功能约束。
- 选定方向后，再单独编写实现提示词，把 V1/V2 的功能契约作为第二阶段输入。
