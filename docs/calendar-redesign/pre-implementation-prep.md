# Opus 等待期间的实施准备

## 当前结论

`refinement-gpt-sol-01` 先作为视觉基线。`refinement-opus5-01` 完成后只做局部机制对比，不再重新选择页面主方向。

在 Opus 返回前，不建议修改正式 `src/`。现在应完成以下三件事：

1. 冻结 Hero 的去留和迁移方式。
2. 把功能契约整理成实施验收表。
3. 准备真实数据下的视觉压力样本，避免概念图只在稀疏月份成立。

## 一、Hero 的处理决策

### 推荐方案：保留能力，合并视觉职责

GPT-sol 左侧已经承担了 Hero 的核心视觉职责，因此正式版本不建议同时保留“全屏 Hero + GPT 工作区左舞台”。两套大立绘会造成：

- 用户打开后先看到 Hero，不能立即扫描日历；
- 向下滚动后又看到第二个大立绘，主视觉重复；
- Hero 的全屏归属色和日历的筛选主题可能互相覆盖；
- 移动端首屏过长，日历被推到下面。

最终应将 Hero 改造成 GPT-sol 左侧的 `WorkspaceStage`，而不是把 GPT-sol 放在旧 Hero 下方。

### Hero 中应保留的部分

| 现有能力 | 处理 |
|---|---|
| `heroCharacters` 的角色挑选逻辑 | 保留，作为舞台候选角色来源 |
| `resolveAffiliation` | 保留，驱动游戏 / 地区 / 阵营标签和局部色彩 |
| `heroImageUrl` 的立绘 / 头像回退 | 保留 |
| 图片加载失败和小图放大限制 | 保留，改为适配舞台容器 |
| 点击立绘打开角色详情 | 保留 |
| 角色轮播 | 可保留，但改成轻量指示点或缩略入口 |
| `onAffiliationChange` | 改为工作区主题上下文，不再污染整页 |

### Hero 中应删除或降级的部分

| 现有视觉/结构 | 处理 |
|---|---|
| `100vh / 100dvh` 全屏高度 | 删除，改为桌面工作区左栏高度 |
| `.hero__scroll-hint` | 删除；工作区不需要“向下看日历”提示 |
| 巨型日期作为首屏主标题 | 缩小为舞台内的日期信息，主导权让给月历 |
| 全屏 `mesh + vignette + grain` | 保留少量舞台氛围，禁止扩散到每个日期格 |
| 全屏自动 Ken Burns | 默认克制；支持动效关闭和静态退化 |
| Hero 独立底边渐隐 | 删除，由工作区背景和边界统一处理 |
| 右侧大段文本区 | 改成 GPT-sol 的顶部上下文 + 底部角色信息 |

### 与 GPT-sol 左舞台的映射

```text
现有 Hero 数据层
  heroCharacters / activeIndex / affiliation / portrait
          ↓
GPT-sol WorkspaceStage
  上方：当前主角、游戏/地区、筛选上下文
  中部：受容器限制的立绘和舞台背景
  下方：角色名、日期、游戏和简短元数据
  边缘：轻量轮播点或打开详情入口
```

这意味着 `Hero.tsx` 的业务数据可以复用，但 JSX 和 CSS 应重新写，不应继续在现有全屏 CSS 上叠加覆盖。

## 二、现在可以准备的真实数据压力样本

当前内置生日数据按月份的角色数量大致为：

| 月份 | 角色数 |
|---|---:|
| 01 | 26 |
| 02 | 15 |
| 03 | 24 |
| 04 | 30 |
| 05 | 22 |
| 06 | 22 |
| 07 | 22 |
| 08 | 30 |
| 09 | 18 |
| 10 | 17 |
| 11 | 19 |
| 12 | 29 |

需要固定以下验收样本：

1. **稀疏月**：事件较少，确认舞台和月历不会显得空洞。
2. **密集月**：4 月或 8 月，确认 7 列网格和行高不会被头像撑破。
3. **同日高密度**：生日 `01-01` 有 7 个角色，必须出现 `+N` 并能打开完整名单。
4. **同日中密度**：`08-18` 有 5 个角色，确认 4+ 规则不与日期数字冲突。
5. **同日低密度**：有 2–3 个角色的日期，确认头像堆叠不会被误读成一个角色。
6. **无图回退**：当前数据中有 `ui-avatars.com` 或缺失立绘的角色，确认文字回退仍然符合视觉系统。
7. **跨游戏同日**：确认游戏色只做小面积识别，不把日期格切成多块主题。
8. **无事件日**：确认空白日期格仍能和补位日、今天区分。

这些样本应在正式实现阶段固定成截图回归清单，而不是由模型随意挑月份。

## 三、现在可以整理的功能入口表

### 常驻工作区

- 月份 / 周期标题。
- 上一个、下一个、今天、年月跳转。
- 月 / 周。
- 生日 / 实装。
- 搜索入口。
- 当前筛选摘要和清除。

### 统一展开面板

- 游戏多选。
- 游戏专属属性、稀有度、武器 / 命途 / 特性、地区 / 阵营 / 组织。
- 显示信息不全的角色。
- 头像显示密度。
- 周起始日。
- 立绘背景、动态效果、主题跟随。
- 只看收藏。

### 更多 / 设置

- 添加 / 编辑角色。
- JSON 导入 / 导出。
- ICS 导出。
- 更新数据。
- 同步进度、结果和最后更新时间。

这张表可以直接作为未来 `WorkspaceControls` 和 `WorkspaceFilters` 的输入，但现在不需要写实现代码。

## 四、Opus 返回后的判断规则

只比较下面五项，不比较“谁的页面元素更多”：

1. 是否仍然一眼识别为 GPT-sol 母版。
2. 真实高密度月份是否比 GPT-sol 更稳。
3. 展开式控件是否更容易理解且不遮挡月历。
4. Hero / 左舞台是否更自然地服务于日历，而不是变成独立海报。
5. 移动端是否同时保留主角表现力和 7 列扫描效率。

合并规则：

- 只合并可单独描述、可单独验收的机制；
- 不合并整块页面、颜色体系或新隐喻；
- 如果 Opus 只是在视觉上更复杂，而没有改善上述问题，则不合并；
- 如果两者都没有明显优点，继续使用 GPT-sol 原方案。

## 五、现在不要做的事

- 不要继续让模型自由设计新的首页。
- 不要在旧 `index.css` 上继续堆覆盖规则。
- 不要先实现所有低频功能，再回头解决主构图。
- 不要同时保留旧全屏 Hero 和新左侧舞台作为正式产品结构。
- 不要用概念图中的“2026 年 8 月”等示例文字替代真实日期逻辑。
- 不要为了截图好看而删掉真实数据中的无图、密集、跨游戏和空状态。
