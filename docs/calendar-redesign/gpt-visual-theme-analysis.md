# GPT 概念图的视觉机制拆解与实现方案

## 结论

GPT 概念图不是“读取角色图片后自动提取主色，再自动生成主题”。四张 SVG 都是手工定义的场景 token：背景渐变、光晕色、左侧立绘压暗、面板表面、边框色、事件色和文字色。

它的视觉效果来自少量层次的组合，而不是很多组件各自换皮：

```text
页面底色
  + 一条全局对角渐变
  + 1 个主径向光晕
  + 1~2 个低透明度模糊光源
  + 左侧立绘裁切
  + 左侧立绘自上而下的底部压暗渐变
  + 右侧半透明深色月历面板
  + 少量角色环、事件点、边框色
```

因此正式实现时应建立“主题 profile + 场景图层”，而不是建立“每个角色一套 CSS”。

## 1. SVG 中实际发生了什么

### 1.1 阿蕾奇诺中性月视图

`01-neutral-month-GPT.svg` 使用：

- 页面底色：深蓝黑到靛紫的对角渐变 `#080b17 → #24203c`；
- 页面主光晕：右上方靛紫径向光晕；
- 辅助光源：右上紫色模糊圆、左下低透明度薄荷色模糊圆；
- 左侧立绘：裁切进圆角舞台，不改变图片本身的色彩；
- 立绘覆盖层：从顶部近乎透明，到底部约 92% 的深色遮罩；
- 右侧月历：`#111426` 的半透明深色面板和白色低透明度边框；
- 事件色：生日珊瑚色、实装 / 匹配事件薄荷色；
- 今天：浅色胶囊；
- 头像：小尺寸圆形头像和游戏 / 事件色环。

这里所谓“从上往下打光”更准确地说是：

> 立绘舞台上的垂直可读性渐变，顶部保留图像，底部逐渐压暗，使底部日期和角色信息可读。

它不是一个真正模拟光源照射角色的 3D 光照系统。角色本身的光影主要来自原始立绘。

### 1.2 纳西妲 / 须弥筛选状态

`02-sumeru-filter-GPT.svg` 做了更明显的上下文主题变化：

- 页面底色从靛蓝黑移向深青绿，再在右下回到紫色；
- 主径向光晕移到左上并使用薄荷青；
- 左侧立绘底部继续使用垂直压暗渐变；
- 左侧舞台边框变为薄荷色；
- 月历面板本身变为深青色表面；
- 月历标题、星期文字和边框略带青绿色；
- 须弥色主要出现在舞台、选中角色头像环和上下文文字；
- 7 列网格的位置、尺寸和日期数字位置保持稳定。

所以用户感受到的是“整张工作区换了色温”，但布局并没有换。它是一个人工定义的地区主题 profile，不是从纳西妲图片像素实时采样出来的。

### 1.3 芙宁娜移动状态

`04-mobile-orbit-GPT.svg` 的处理更克制：

- 页面仍然是深靛到紫红的基础渐变；
- 顶部使用紫色径向光晕；
- 右上只有一个低透明度珊瑚色模糊光源；
- 左侧 / 顶部立绘舞台使用珊瑚色边框；
- 立绘底部继续使用垂直压暗渐变；
- 日历面板没有改成整块珊瑚色，只保留珊瑚事件点和今天状态。

因此，芙宁娜图不是“须弥主题的移动版”，而是“中性靛紫底 + 角色 / 游戏强调色”的弱上下文版本。它证明了主题强度可以按状态和视口调整。

## 2. 需要采用的视觉模型

### 2.1 主题来源分三层

不要让任意角色名直接决定一套主题。主题来源按优先级分三层：

1. **中性基础主题**：应用默认深靛色和文字 / 表面 token。
2. **游戏或地区上下文**：由现有 `useTheme` 和 `resolveAffiliation` 提供游戏级 / 地区级颜色。
3. **角色强调色**：只在当前舞台主角或详情页中使用，用于边框、光晕、事件环和局部强调。

地区主题存在时，地区优先于游戏色；地区主题不存在时回落到游戏色；没有明确上下文时回到中性主题。

### 2.2 不建议第一版做实时图片取色

可以通过 Canvas 从角色立绘提取主色，但第一版不建议这样做：

- 角色立绘明暗差异很大，取出的颜色不一定适合文字和控件；
- 同一个角色不同裁切可能得到不同颜色；
- 过亮、过饱和或偏灰的图片会让界面对比度不稳定；
- 跨域图片、加载失败和移动端性能会增加复杂度；
- 视觉结果难以预测和设计审查。

第一版应使用人工审校的 profile。以后如果需要动态取色，也只能作为“角色光晕候选色”，经过饱和度、亮度和对比度限制后使用，不能直接覆盖全站主题。

## 3. 建议的 Theme Profile

每个 profile 只定义颜色和图层强度，不定义布局：

```text
ThemeProfile {
  baseStart          页面渐变起点
  baseMid            页面渐变中段
  baseEnd            页面渐变终点
  haloPrimary        主径向光晕颜色
  haloSecondary      第二光源颜色
  stageDeep          立绘舞台底部压暗颜色
  stageBorder        舞台边框颜色
  surface            月历面板表面颜色
  surfaceBorder      月历面板边框颜色
  accent              当前上下文强调色
  eventBirthday      生日事件色
  eventRelease       实装事件色
  contextStrength    普通工作区的主题强度
  heroStrength       全屏 Hero 的主题强度
}
```

建议至少有：

- `neutral`：阿蕾奇诺中性月视图的深靛基准；
- `genshin`：原神游戏级回落主题；
- `genshin-sumeru`：纳西妲 / 须弥的深青绿 + 薄荷光晕；
- `hsr`：星穹铁道游戏级主题；
- `zzz`：绝区零游戏级主题；
- `honkai3`：崩坏3游戏级主题。

角色级 profile 不应一开始为 200 多个角色逐一建立。阿蕾奇诺、芙宁娜等角色可以通过 `accent` 和 `haloSecondary` 使用角色强调色，但仍继承游戏 / 地区基础 profile。

## 4. 状态强度规则

### 默认月历

- 基础背景保持深靛色家族；
- 光晕最多 1 个主光源 + 1 个辅助光源；
- 左侧舞台有明显立绘裁切和底部压暗；
- 月历表面保持深色中性；
- 角色色只进入舞台边框、头像环、事件点和摘要；
- 不让每个日期格单独换背景或材质。

### 选择游戏

- 页面整体允许轻微色温变化，但不超过“仍然是同一个产品”的范围；
- 左侧舞台和事件环体现游戏色；
- 月历表面只做非常轻的色相偏移；
- 网格、日期位置和操作位置不变。

### 选择地区 / 阵营

- 左侧舞台使用地区光晕、边框和身份文字；
- 月历表面可以出现轻微地区色温，参考须弥图，但不要让所有日期格重新着色；
- 选中角色的头像环使用地区色；
- 其他游戏没有细分映射时回落到游戏级主题。

### 全屏 Hero

全屏 Hero 是最适合使用强主题的地方：

- 整屏背景可以更明显地偏向当前地区 / 游戏；
- 可以使用 1–2 个较大的模糊光源；
- 立绘可以更大，底部压暗更明显；
- 边框和标题可以使用角色强调色；
- 仍需限制动画、遵守 `prefers-reduced-motion`；
- 关闭后回到日历，日历的筛选、月份和选中状态不丢失。

这不是“整页换色被禁止”，而是把强换色放到了语义更清楚的沉浸状态。

## 5. 图层顺序和排布

### 桌面工作区

```text
App background
  ├─ 对角基础渐变
  ├─ 1 个全局主光晕
  ├─ 1 个低透明度辅助光源
  ├─ 左侧角色舞台
  │   ├─ 裁切立绘
  │   ├─ 顶部轻信息层
  │   ├─ 立绘底部垂直压暗渐变
  │   └─ 角色名 / 日期 / 游戏 / 地区
  └─ 右侧月历面板
      ├─ 半透明深色表面
      ├─ 月份标题与导航
      ├─ 7 列日期网格
      ├─ 头像、头像环、事件点
      └─ 条件显示的当天信息条
```

这里没有“从左侧舞台向右侧月历的一条实体渐变”。用户感受到的过渡主要来自：

- 页面全局对角渐变；
- 左右区域共享的深色表面；
- 左舞台的光晕和右侧面板的低透明度边框；
- 中间细分隔线；
- 同一套文字和状态色。

### 移动工作区

- 顶部保留一个有限高度的角色舞台；
- 舞台底部压暗，文字叠在可读区域；
- 日历继续使用同一套背景基准；
- 角色强调色只通过边框、光晕、事件点和头像环进入；
- 全屏 Hero 点击后才使用更强的背景和光晕。

## 6. 视觉验证方案

在正式实现前，不需要继续让模型自由设计。只需要用同一套 profile 生成以下静态状态：

1. 阿蕾奇诺 / 中性月历：验证深靛基准和舞台底部压暗；
2. 纳西妲 / 须弥筛选：验证深青绿主题强度；
3. 芙宁娜 / 移动端：验证弱角色强调色；
4. 无细分阵营的星穹铁道：验证游戏级回落；
5. 高密度日期：验证主题变化不会影响头像密度和日期位置；
6. 全屏 Hero：验证强主题是否适合沉浸状态。

每个状态只改变 profile token，不改变 DOM 结构、网格尺寸、控件位置和头像规则。

### 验收问题

- 去掉光晕后，页面是否仍然成立？
- 切换主题后，用户是否仍然知道自己在同一个日历？
- 日期、头像、今天和选中状态是否仍然可读？
- 纳西妲的青绿色是否集中在舞台和局部表面，而不是变成满屏荧光？
- 芙宁娜的珊瑚色是否作为角色强调，而不是覆盖整个移动页面？
- 全屏 Hero 是否比默认月历允许更强的色彩和光线？
- 主题变化是否只替换 token，而不是触发布局跳动？

## 7. 最终方案修正

GPT 的视觉重点不是“自动提取颜色”，而是：

> 通过人工策划的角色 / 游戏 / 地区主题 token，叠加有限数量的舞台光照层和表面层，让同一套日历骨架获得不同世界观气质。

正式实现应采用：

1. GPT 风格作为图层和比例基准；
2. 现有 `resolveAffiliation` 和 `useTheme` 作为主题上下文来源；
3. 人工审校的 `ThemeProfile` 作为颜色和光晕配置；
4. 默认工作区采用中等强度变化；
5. 全屏 Hero 允许更强的整屏主题；
6. 不给每个日期格做独立材质；
7. 不在第一版做不稳定的实时图片取色；
8. 所有主题状态共享同一套网格、控件、头像和详情结构。
