# GPT 主视觉与 Opus5 局部机制审核

## 结论先行

最终方案不应是 GPT 和 Opus5 的平均，而应是：

> GPT 负责整体美学、构图、留白和舞台感；Opus5 负责经过收敛的头像密度、控件分层和真实数据边界。

GPT 的视觉方向已经冻结为主方案。Opus5 不再参与整体风格投票，只作为局部交互与信息架构参考。

Opus5 的方案不能原样搬入，主要原因是：

- 顶栏常驻控件过多，形成一串胶囊，削弱 GPT 的留白；
- 每个单角色日期都显示名字，月历会从“视觉轨道”变成文字列表；
- 筛选面板虽然不遮挡月历，但打开后左侧舞台几乎变成密集设置面板；
- 固定 6 行月历有稳定性优点，但会在部分月份增加不必要的空行；
- 桌面底部当天条有价值，但不应在没有选择时永久增加一层信息。

## 1. 审核方法

不再比较“哪个页面更漂亮”，因为 GPT 已经确定为美学母版。局部机制按以下权重审核：

| 维度 | 权重 | 判断问题 |
|---|---:|---|
| 与 GPT 美学兼容性 | 30 | 移植后是否仍有留白、主次和舞台感 |
| 日历扫描效率 | 25 | 日期、事件密度和今天是否能快速识别 |
| 高密度数据稳定性 | 20 | 4 月、8 月和 01-01 等压力样本是否不溢出 |
| 控件可达性 | 15 | 功能是否完整、入口是否容易理解 |
| 实现风险 | 10 | 是否能复用现有业务逻辑，是否引入额外状态复杂度 |

审核对象限定为：控件、头像密度、信息位置、排布、状态变化和真实数据边界。Hero 的整体美学另行服从 GPT 方案。

## 2. 逐项决策

### 2.1 三档头像密度：采用，做一次收敛

Opus5 这一部分是最值得合并的机制。它的优点是：

- 日期数字固定在左上，不会被头像挤动；
- 单角色、2–3 角色、4+ 角色有明确尺寸差异；
- 4+ 角色只显示有限头像并使用 `+N`，不把密集日期撑爆；
- 规则用真实 4 月数据和全年 20 人同日压力样本验证过。

最终规则：

| 当天人数 | 桌面默认模式 | 移动端 | 文字策略 |
|---|---|---|---|
| 1 | 48–56px 单头像 | 30–34px 单头像 | 默认不显示名字；选中日期或卡片模式显示短名 |
| 2–3 | 30–36px 堆叠，重叠约 25–35% | 2 人 24–26px，3 人 18–22px | 默认不逐个显示名字；显示数量或选中态摘要 |
| 4+ | 22–26px，最多 3 个 + `+N` | 18–20px，最多 3 个 + `+N` | 只显示 `+N` / 共 N 位，点击进入当天名单 |

这里有一个重要改动：不直接采用 Opus5 的“每个单角色头像下都显示角色名”。在真实月份中，这会让几十个日期格同时出现细小文字，降低 GPT 方案的留白和扫描速度。

角色名字应放在：

- 当前选中日期的底部信息条；
- 点击日期后的当天名单面板；
- `card` 显示模式；
- 搜索结果和角色详情。

保留 `avatar / card / compact` 三种用户偏好，但它们只改变文字密度和头像大小，不改变三档布局原则：

- `avatar`：GPT 默认视觉，头像优先，文字最少；
- `card`：头像 + 短名，适合需要识别名称的用户；
- `compact`：小头像 / 色点 + `+N`，适合高密度扫描。

### 2.2 日期数字和事件位置：采用

每个日期格必须固定：

- 日期数字在左上；
- 事件状态标记在右上或日期行末；
- 头像 / 头像堆叠位于日期行下方的稳定区域；
- `+N` 与头像在同一事件区域，不改变格子高度。

这比 GPT 初稿中头像有时浮在格线附近更稳。固定位置是结构机制，不会破坏 GPT 美学。

事件标记只保留小面积表达：

- 有事件：一个小点或短线；
- 生日 / 实装混合时：允许使用第二种形状，但必须有图例或当天详情解释；
- 不要在每个格子放大标签或彩色底块。

### 2.3 顶栏控件：采用 Opus5 的分组思路，拒绝原样数量

Opus5 的功能覆盖正确，但顶栏同时出现搜索、月周、生日实装、筛选摘要、筛选显示、更多等多个胶囊，长期使用会像控制面板。

最终桌面顶栏只保留五个视觉组：

1. 搜索入口；
2. 月 / 周；
3. 生日 / 实装；
4. 当前筛选摘要 + 筛选入口；
5. 更多菜单。

这些功能可以常驻，但视觉上必须做成 GPT 风格的轻量文字 / 细边界分组，而不是每个都做成独立厚重胶囊。顶栏不要出现虚构的 `CALENDAR / COLLECTION / INSIGHTS` 导航。

日历卡内部常驻：

- 月份标题；
- 上一月 / 下一月；
- 今天；
- 点击月份标题跳转年月。

不应放进顶栏的功能：

- 添加 / 编辑；
- JSON 导入导出；
- ICS；
- 同步和最后更新时间；
- 周起始日、立绘背景、动效、主题跟随。

### 2.4 筛选 / 显示面板：采用点击展开，但做渐进披露

答案是：应该采用点击展开，不应让 Opus5 的所有筛选 chip 常驻。

推荐机制：

- 顶栏只显示一个“筛选”入口和当前摘要，例如“全部游戏 · 288 位”或“原神 · 须弥 · 6 个条件”；
- 点击后，在桌面端从左侧舞台底部升起一个与舞台同宽的面板；
- 面板不遮挡右侧月历；
- 面板内部先选择游戏，再显示该游戏的地区 / 阵营、属性、稀有度、武器 / 命途 / 特性；
- 显示密度、周起始日、只看收藏和信息不全选项放在“显示”分组，不与游戏筛选同时全部展开；
- 完成、点击外部或 Escape 收起；
- 收起后摘要仍留在顶栏。

这样保留了 Opus5 的“从左侧升起、不遮挡日历”优点，同时保护 GPT 默认状态的留白。

移动端：

- 点击“筛选”后打开底部抽屉或近全屏面板；
- 抽屉内部独立滚动；
- 固定“清除”和“应用 / 关闭”操作；
- 不要求用户在主月历首屏看到所有筛选项。

### 2.5 更多菜单：采用

Opus5 的 `⋯` 入口适合收纳低频功能。菜单中放：

- 添加 / 编辑角色；
- JSON 导入 / 导出；
- ICS 导出；
- 更新角色数据；
- 最后更新时间；
- 立绘背景、动态效果和主题跟随。

“更多”不应变成第二个大型面板；只需要清晰的菜单或设置抽屉。更新中的进度和失败信息必须使用明确的状态区域或 toast，不依赖颜色。

### 2.6 日历底部当天条：条件显示

Opus5 的底部当天条有实际价值：它把当前日期的角色、数量、事件语义和“查看当天”入口集中起来，尤其适合 `+N` 日期。

但它不应在中性状态永久占据一行。最终规则：

- 未选择日期：不显示大条；可保留一条极轻的“下一事件”文本；
- 点击日期或 `+N`：显示当天信息条，包含日期、第一位角色、总数和“查看当天”；
- 移动端：保留 GPT / Opus 的下一事件卡，因为移动端需要一个明确的下一个动作；
- 当天名单打开后：信息条变成返回入口，不再重复堆叠角色内容。

### 2.7 固定 6 行月历：不原样采用

Opus5 固定 6 行的优点是月切换时高度不跳动，但它会在 5 行足够的月份留下明显空行。

建议采用折中方案：

- 月视图仍按真实完整周生成 5 或 6 行；
- 工作区外框高度保持稳定；
- 5 行月份让每行略微增高，6 行月份自动收紧；
- 头像尺寸必须受单元格内部空间限制，不能撑开网格；
- 视觉回归必须覆盖 5 行和 6 行月份。

这样保留稳定的外部构图，又不牺牲月份空间效率。

### 2.8 游戏 / 地区颜色：按状态分层采用

这里不是“整页换色一定更耗资源”，而是要区分默认工作区和沉浸状态。CSS 渐变本身通常不是主要性能风险；真正的风险是状态变化过重、文字对比度变化、页面像切换成另一套产品，以及用户在筛选时失去稳定的空间参照。

采用以下边界：

- 游戏色：头像环、事件点、筛选摘要中的小色点；
- 地区 / 阵营色：左侧舞台光晕、主角信息、被选中角色的环；
- 默认日历工作区的中性底、日期文字、网格和控件位置保持稳定；
- 不因普通筛选而让整个工作区突然变成另一种产品主题；
- 点击左侧进入全屏 Hero 沉浸状态后，可以让整屏背景 / 舞台明显偏向当前游戏或地区色，因为此时用户已经进入“角色观看”状态，强烈的色彩变化有明确语义；
- 如果产品以后增加“地区主题预览”模式，也可以在明确的模式切换下使用整屏换色，但不能让每个日期格各自换材质；
- 星穹铁道和崩坏3没有现成细分映射时，只使用游戏级主题。

因此，GPT 初稿的整页青绿色并非效果不好或技术上不可行，而是不应作为普通月历筛选的默认反馈。它更适合移动到全屏 Hero 或明确的沉浸主题状态。每个日期格单独换材质仍然不建议，因为它会把日期拓扑切碎、提高视觉噪声，并增加大量状态组合，而不是因为单纯的 CSS 资源消耗。

## 3. 位置与排布基准

### 桌面端

```text
顶栏：品牌标题 | 搜索 | 月/周 | 生日/实装 | 筛选摘要 | 更多

工作区：
  左 30–34%：GPT 角色舞台（可点击进入沉浸 Hero）
  右 66–70%：GPT 月历卡
                标题 + 月份导航 + 今天
                星期行 + 7 列月格
                条件显示的当天信息条

筛选展开：从左侧舞台底部升起，只覆盖左侧舞台
```

### 移动端

```text
顶部：中文标题 | 搜索图标 | 更多图标
角色舞台预览：有限高度，不自动推走月历
月份标题：上月 | 月份 | 今天 | 下月
模式：月/周 + 生日/实装 + 筛选
7 列月历：固定日期位置，头像按三档缩小
下一事件 / 当天信息卡
```

移动端不应把所有桌面顶栏控件压缩在同一行；周起始日、显示密度、动效和导入导出都进入面板。

## 4. Hero 与左侧舞台的关系

最终默认状态仍是日历工作区。左侧是 GPT 风格的角色舞台预览，点击后进入沉浸式 Hero 覆盖层。

- GPT 决定舞台的颜色、留白、字级和裁切气质；
- Opus5 只提供角色身份块、归属色收敛和小型角色状态信息；
- 旧 Hero 的轮播、归属解析、图片回退和点击详情能力可以复用；
- 旧 Hero 的全屏 `100vh`、Scroll 提示、巨型日期和全屏 grain 不直接保留；
- Hero 覆盖层和角色详情要分工：Hero 负责沉浸观看，详情负责字段、收藏、编辑和 ICS。

左侧舞台本身点击区域应有明确的展开按钮或提示，不能与筛选面板入口冲突。

## 5. 头像和资源质量的额外验收

Opus5 发现真实数据中存在“URL 可加载但内容不是角色头像”的资源。正式实现不能只判断 `<img>` 是否加载成功。

需要定义资源状态：

1. 正常角色头像；
2. URL 缺失或加载失败；
3. `ui-avatars.com` 文字占位图；
4. CDN 粉底名牌等非角色图像。

第 2–4 类在月历中统一使用首字回退，但详情页可保留原 URL 的更大预览并给出失败状态。回退仍要保留游戏色环、可点击性和无障碍名称。

## 6. 最终审核结论表

| 机制 | 决策 | 原因 |
|---|---|---|
| GPT 深靛舞台 + 34/66 构图 | 保留 | 已确定的美学母版 |
| Opus 三档头像密度 | 采用并去掉默认名字 | 稳定、真实数据验证过，但名字过多会变吵 |
| 日期固定左上 + 头像固定下方 | 采用 | 防止布局跳动 |
| Opus 顶栏全部胶囊 | 改造 | 功能正确但视觉过密 |
| 单一筛选 / 显示展开入口 | 采用 | 保留功能且保护默认留白 |
| 左侧舞台底部筛选面板 | 采用并渐进披露 | 不遮挡日历，但不能一次展示所有 chip |
| `⋯` 更多菜单 | 采用 | 适合低频维护功能 |
| 每格角色名 | 仅 card / 选中态 | 默认月历需要留白 |
| 底部当天信息条 | 条件显示 | 有用但不应常驻占空间 |
| 固定 6 行 | 不原样采用 | 稳定性和空间效率需折中 |
| 默认工作区整页地区换色 | 改为受控状态 | 普通筛选时过重；可移入全屏 Hero |
| 头像 URL 加载即视为有效 | 拒绝 | 真实数据有非角色占位图 |

## 7. 进入实现前的冻结条件

以下事项确认后再写前端：

1. 默认 `avatar` 模式是否采用“头像优先、名字不常驻”；建议采用。
2. 顶栏是否限制为五个视觉组；建议采用。
3. 筛选是否统一从左侧舞台底部展开；桌面建议采用，移动端改底部抽屉。
4. 底部当天条是否条件显示；建议采用。
5. 月历是否 5 / 6 行动态生成但外框稳定；建议采用。
6. Hero 是否作为左侧舞台的二级沉浸状态；建议采用，并允许点击后使用全屏覆盖层。

在这些条件冻结后，才进入展示层实现。不要边写 CSS 边重新争论整体方向。
