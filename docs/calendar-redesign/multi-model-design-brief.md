## 0. 如何使用这份文档

本次重绘采用“一个事实源、多个独立提案、一个匿名评审、一个最终实现者”的流程。

1. 本文第 1-7 节是已经完成的功能审计，也是所有模型共同使用的事实源。
2. 将第 8 节“候选设计模型提示词”分别交给 2-3 个模型。每次使用前，把 `{{CANDIDATE_ID}}` 替换成不同的匿名编号，例如 `candidate-01`、`candidate-02`。
3. 候选模型之间不要共享回答，也不要让后一个模型评价或延续前一个模型的视觉方向。
4. 收集候选方案后，隐去模型名称，只保留候选编号。
5. 将候选方案和第 9 节“独立评审模型提示词”交给另一个模型做盲评。
6. 评审结束后再确定最终实现方向。不要让多个模型同时修改正式前端，也不要把多个方案机械拼接成一个方案。

候选模型本轮的职责是“提出可实现、可比较的完整设计方向”，不是直接重写生产代码。若模型具备浏览器或原型能力，可以制作隔离原型和截图，但不得修改现有 `src/` 生产实现。

## 1. 产品目标与用户核心任务

这是一个面向米哈游游戏玩家的角色生日/实装纪念日日历。它不是营销官网，也不是通用企业 Dashboard。

用户的核心任务按优先级排序：

1. 快速查看某个月或某周有哪些角色生日/实装纪念日。
2. 按游戏、属性、稀有度、武器/命途/特性、地区/阵营/组织筛选角色。
3. 搜索一个角色并定位到对应月份。
4. 查看角色详情、立绘和归属信息。
5. 收藏角色，只看本机收藏。
6. 导出 ICS 日历提醒或 JSON 数据。
7. 添加、编辑或导入本地角色数据。
8. 更新已发布的角色数据。

产品重绘的核心目标：

- 日历必须成为工作区的视觉和交互中心。
- 用户能快速扫描日期、角色密度和游戏归属。
- 控件很多，但不能让所有控件拥有相同视觉权重。
- 游戏和阵营应具有可感知的差异，同时整个应用仍像同一个产品。
- 桌面端适合反复筛选和扫描，移动端优先保证日历可见和触控效率。

## 3. 必须保留的功能契约

候选方案允许重新组织控件、修改组件结构、改变视觉表达，但以下行为必须保留。

### 3.1 日历导航与日期

- 月视图和周视图切换。
- 上一个月/周、下一个月/周、回到今天。
- 当前标题显示年份和月份。
- 点击标题可通过月份选择器跳转年月。
- 支持周日或周一作为一周开始。
- 月视图展示包含前后月补位日期的完整周网格。
- 非闰年遇到 2 月 29 日的年度生日映射时，必须有明确、不会误导用户的处理。
- 今天、当前月份、非当前月份、有角色日期、无角色日期必须可区分。

### 3.2 日期语义

- 全局支持 `birthday` 和 `release` 两种日期模式。
- 生日按 `MM-DD` 每年重复展示。
- 首次实装日期来自 `YYYY-MM-DD`，日历按月日展示周年纪念，详情可展示完整日期。
- 星穹铁道没有可靠官方生日，必须强制使用实装日期。
- 崩坏3当前没有完整实装日期，必须回落到生日。
- 不能为了统一 UI 而让这些游戏出现空日历或错误日期。

### 3.3 角色展示

- 月视图支持头像、卡片、紧凑三种显示模式。
- 周视图需要呈现角色名称、游戏归属，并根据显示模式合理调整密度。
- 角色可能没有头像或立绘，必须提供稳定的文字/首字回退。
- 图片加载失败不能破坏日历布局。
- 同一天角色过多时，必须显示数量或“查看更多”入口，并能打开当天全部角色面板。
- 点击日期格中的角色、周视图角色或当天面板角色，均可进入同一角色详情流程。

### 3.4 游戏与筛选

支持四个游戏：

- 原神 `genshin`
- 崩坏：星穹铁道 `hsr`
- 绝区零 `zzz`
- 崩坏3 `honkai3`

筛选状态按游戏隔离，不能混用各游戏字段。每个游戏的标签语义如下：

| 游戏 | elements | weapons | regions |
|---|---|---|---|
| 原神 | 元素 | 武器 | 地区 |
| 星穹铁道 | 属性 | 命途 | 阵营 |
| 绝区零 | 属性 | 特性 | 阵营 |
| 崩坏3 | 属性 | 类型 | 组织 |

必须保留：

- 游戏多选。
- 当前正在编辑筛选条件的游戏上下文。
- 每个游戏独立的元素/属性、稀有度、武器类字段、地区类字段。
- “显示信息不全的角色”。
- 活跃筛选数量。
- 清除全部筛选。
- 游戏被取消选择后，筛选面板自动切到下一个仍选中的游戏。
- 如果所有游戏都被取消选择，需要有合理空状态，不能显示错误数据。

### 3.5 桌面与移动筛选

- 桌面端存在可折叠的筛选侧栏，折叠后日历应回收空间。
- 移动端隐藏桌面侧栏，通过筛选按钮打开底部面板或等价的移动交互。
- 移动筛选内容可独立滚动。
- 移动筛选必须有清除和应用/关闭动作。
- 点击遮罩可关闭，关闭按钮有明确的可访问名称。

### 3.6 搜索

- 搜索范围是全部角色，不只是当前日历筛选后的角色。
- 可搜索中文名、英文名、游戏、生日、属性、武器/命途/特性、地区/阵营/组织。
- 匹配结果按名称优先级排序，默认最多显示 8 项。
- 支持键盘 `ArrowUp`、`ArrowDown`、`Enter`、`Escape`。
- 搜索结果显示角色头像/回退、名称、游戏、当前日期语义和元数据。
- 选中角色后清空搜索，跳转到其对应月份并打开角色详情。

### 3.7 角色详情

- 展示中文名、英文名、游戏、生日或实装日期、稀有度、元素/属性、武器/命途/特性、地区/阵营/组织。
- 支持头像缺失回退。
- 存在立绘时可以显示立绘背景。
- 支持“详情/仅看立绘”切换。
- 支持动态立绘开关；关闭或设备要求减少动画时必须退化为静态效果。
- 支持收藏/取消收藏。
- 支持导出单个角色 ICS。
- 支持进入编辑流程。
- 点击遮罩或关闭按钮可关闭。

### 3.8 添加、编辑和导入

- 添加与编辑共用流程。
- 表单包含角色名、英文名、游戏、生日、稀有度、元素/属性、武器类字段、地区类字段、头像地址。
- 支持本地图片上传并即时预览。
- 支持单条或数组 JSON 导入。
- 必填项和错误提示不能仅靠颜色表达。
- 当前实现没有角色删除 UI，设计方案不得擅自增加危险删除动作。

### 3.9 收藏、导出和同步

- 角色收藏保存在本机。
- 可切换“只显示收藏”。
- 显示收藏数量。
- 可导出全部角色 JSON。
- 可导出有效生日/实装纪念日的 ICS。
- ICS 无有效事件时需要明确反馈。
- 可更新已发布的角色 JSON 数据。
- 更新时显示进度、成功或失败回退状态。
- 显示最后更新时间。
- 不引入账号、云同步、邮件服务或后端任务。

### 3.10 持久化偏好

以下偏好由现有逻辑持久化，重绘不能让它们失效：

- 角色数据和手动添加数据
- 显示模式
- 周起始日
- 游戏专属筛选
- 立绘背景开关
- 动态效果开关
- 生日/实装日期模式
- 收藏角色
- 主题跟随模式
- 最后同步时间

## 4. 游戏与阵营上下文主题契约

### 4.1 当前能力

项目已有两层主题信息：

1. `useTheme` 负责中性主题和游戏级主题。选中角色或只保留一个游戏时可以跟随游戏。
2. `resolveAffiliation(character)` 负责更细的地区/阵营解析，返回：
   - `id`
   - `name` / `nameEn`
   - `tagline`
   - `colors.key`
   - `colors.accent`
   - `colors.deep`
   - 可选背景信息

当前细分程度：

- 原神：已按蒙德、璃月、稻妻、须弥、枫丹、纳塔、至冬、坎瑞亚等地区解析。
- 绝区零：已按狡兔屋、维多利亚家政、白祇重工、卡吕冬之子、对空六课等多个阵营解析。
- 星穹铁道：目前只有游戏级通用主题，细分星球/阵营尚未完成。
- 崩坏3：目前只有游戏级通用主题，细分组织尚未完成。

候选方案不得虚构缺失的星铁/崩坏3阵营映射。

### 4.2 期望的三级语义

| 层级 | 允许变化 | 必须稳定 |
|---|---|---|
| 游戏 | 基础色调、强调色家族、图形气质 | 页面结构、核心控件位置、信息层级 |
| 阵营/地区 | 次级色、低对比纹理、边框/分隔符语言、短暂过渡效果 | 日历网格尺寸、文字可读性、交互规则 |
| 角色 | 头像、立绘、名称和属性信息 | 导航方式、弹窗结构、操作含义 |

### 4.3 效果设计要求

用户点击不同游戏、地区或阵营的角色时，应获得“这是不同归属”的视觉反馈，但不能让页面像切换到另一个产品。

候选模型需要设计一套可扩展的 Context Theme System，而不是为每个阵营复制一套组件。系统至少说明：

- 哪个组件接收当前角色/阵营上下文。
- 哪些 design tokens 发生变化。
- 哪些区域允许出现纹理或局部装饰。
- 点击后的过渡时长、范围和退出方式。
- 连续快速切换角色时如何避免闪烁或动画堆积。
- 立绘缺失、阵营未知、颜色过亮时如何回退。
- `motionEnabled=false` 和 `prefers-reduced-motion` 下如何静态退化。
- 如何保证正文对比度、焦点环和游戏色识别。

推荐探索三种强度，但候选模型最终只能选择并完整论证一种：

- 克制：颜色、边框、纹理静态变化。
- 平衡：静态主题加 150-350ms 的一次性局部过渡。
- 强表现：局部粒子/光效或场景化效果，但必须提供性能预算和可访问退化。

这不是要求所有效果都保守。玻璃、霓虹、发光、纹理、粒子和卡片都可以局部使用，但必须能说明它承载了什么游戏/阵营语义。仅以“更高级”“更有科技感”为理由不成立。

## 5. 响应式、可访问性和性能底线

### 5.1 目标视口

每个候选方案必须分别描述或展示：

- 1440 × 900：主桌面
- 1280 × 800：紧凑桌面
- 1024 × 768：平板/断点边界
- 768 × 1024：竖屏平板
- 390 × 844：主流手机
- 360 × 800：窄手机

### 5.2 响应式底线

- 任何目标视口不得出现页面级横向滚动。
- 7 列月历不能被头像、卡片或长角色名撑宽。
- 角色名、长阵营名和“崩坏：星穹铁道”等文本必须安全换行或截断。
- 触控按钮必须有稳定尺寸，动态内容不能造成布局跳动。
- 移动端打开筛选后必须仍可理解当前筛选上下文。
- 弹窗高度超过视口时必须内部滚动，关闭动作不能离开屏幕。

### 5.3 可访问性底线

- 所有可点击元素使用语义化按钮/输入控件。
- 键盘焦点清晰可见。
- 不能只用颜色表达选中、今天、收藏或错误。
- 搜索维持 combobox/listbox 语义和键盘操作。
- 弹窗和筛选面板需要明确标题、关闭名称和遮罩行为。
- 尊重 `prefers-reduced-motion`。
- 动态阵营效果不得造成持续闪烁、快速大面积亮度变化或文字对比失效。

### 5.4 性能底线

- 日历滚动、月份切换和弹窗打开应保持流畅。
- 不为每个日期格创建持续运行的粒子或滤镜动画。
- 避免大面积高强度 `backdrop-filter`、多层模糊和无限动画。
- 角色图片使用现有资源和懒加载策略，不依赖随机外部素材。
- 阵营切换效果优先使用 CSS token 和单一效果层，不复制大量 DOM。

## 6. 视觉问题假设与设计自由度

以下是需要候选模型验证的问题假设，不是指定答案：

- 当前顶栏同时承载搜索、显示模式、日期模式、主题、动效、周起始日、筛选、收藏、导出和同步，视觉优先级容易扁平。
- 日历有三种显示模式和大量角色头像，日期格需要在“信息密度”和“扫描效率”之间建立稳定规则。
- 深色主题、游戏色、阵营色和角色立绘同时存在时，容易互相争夺注意力。
- 如果每个控件、筛选标签和日期格都各自带框，会产生强烈的容器噪声。
- 如果只追求大图和氛围，日历会退化为 Hero 的附属内容。
- 如果只追求工具密度，又会失去米哈游角色内容应有的情绪和辨识度。

候选模型拥有以下自由：

- 重排工作区的信息架构。
- 把低频设置收进菜单、Popover 或设置面板，只要功能仍容易发现。
- 重新设计月视图和周视图的视觉表达。
- 重新设计筛选侧栏宽度、折叠形态和移动面板形态。
- 重新设计角色详情的布局、立绘比例和操作区。
- 建立新的 token、排版、间距、形状和动效体系。
- 在不增加业务功能的前提下，使用现有数据增加辅助视觉信息，例如游戏标识、当天数量和筛选摘要。

候选模型不得：

- 删除现有功能来换取画面简洁。
- 使用虚假角色、虚假事件、虚假统计或虚假阵营。
- 把日历改成营销落地页、数据 KPI Dashboard 或卡片瀑布流。
- 只做换色、改圆角、加阴影等局部美化。
- 默认堆叠玻璃拟态、霓虹渐变、装饰性渐变球或无意义粒子。
- 以现有 CSS 类名和布局为设计起点。
- 建议重写业务数据层作为视觉方案的前提。

## 8. 候选设计模型提示词

## 10. 人工执行建议

为了让比较更接近一个小型设计实验，建议保持以下条件一致：

- 所有候选模型使用同一份仓库状态和同一版本任务书。
- 每个候选使用独立新会话，不携带其他候选的对话历史。
- 不向候选提供“另一个模型已经怎么做”的信息。
- 为每个候选分配相近的时间、工具和输出范围。
- 原型截图使用相同视口和相同代表日期/角色。
- 评审前隐藏模型名称，只保留候选编号。
- 先评方案，再选实现者；不要因为某模型更会写代码就自动采用它的视觉方向。

如果第一轮候选差异仍然很小，下一轮不要简单要求“更大胆”。应指出它们共享的假设，例如“都保留了现有双行顶栏”或“都把角色详情做成居中卡片”，再要求新候选主动推翻其中一个假设，同时继续遵守功能契约。
