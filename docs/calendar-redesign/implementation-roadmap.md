# GPT-sol 母版落地路线图

## 0. 当前决策

当前暂定使用 `candidates/refinement-gpt-sol-01/` 作为视觉基线，原因不是它的自评分数，而是它在现有候选中同时满足了三件事：

1. 保留 GPT 母版的左舞台 / 右月历构图。
2. 解决了虚构导航、控件过多和头像密度问题。
3. 没有为了“看起来有变化”重新发明一套视觉隐喻。

`refinement-opus5-01` 已经在生成中。让它完成当前任务即可，但它不再拥有重新选择主方向的权力。它只能提供局部参考，例如更好的控件展开方式、头像堆叠细节或移动端处理。如果 Opus5 结果没有明确优于 GPT-sol 的某个局部机制，就不合并。

不要继续发起更多自由设计候选，也不要把多个候选的页面拼成第三套设计。

## 1. 两个冻结点

### 视觉冻结点

在开始写生产 CSS 前，建立一页“视觉合同”，至少冻结：

- 桌面左舞台 / 右月历的比例范围（目标约 34 / 66）。
- 深靛中性底、角色舞台光晕和状态色的分工。
- 7 列月视图和日期数字的固定位置。
- 单角色、2–3 角色、4+ 角色三档头像规则。
- 详情页的“信息区 + 大立绘”关系。
- 移动端的“主角舞台 → 月历 → 下一事件 / 详情”顺序。
- 中文产品名称和真实功能名称；删除 `INSIGHTS` 等不存在的功能。

冻结后，后续模型不得再改变页面隐喻、主构图、主色方向和头像密度机制。可以调整字号、间距、边框、阴影和控件文案，但必须说明原因。

### 功能冻结点

将“功能保留”定义为“行为仍然可达”，而不是“每个按钮都常驻在首屏”。低频功能可以进入统一的“更多 / 设置”面板，但不能无说明地删除。

## 2. 功能优先级和取舍原则

### P0：首屏和每天都会用到的功能

这些功能必须在第一版新视觉中可直接使用：

- 月视图和周视图。
- 上一个 / 下一个月或周、回到今天、跳转年月。
- 生日 / 首次实装日期切换，以及星铁和崩坏3的日期回落语义。
- 7 列月历、今天、当前月补位日期、有事件日期和无事件日期的区分。
- 点击日期、角色和 `+N` 进入当天名单或角色详情。
- 角色头像 / 立绘缺失时的文字回退。
- 搜索角色并跳转到对应月份。
- 游戏筛选入口、当前筛选摘要和清除筛选。
- 桌面和移动端的基本可用布局。

### P1：重要但不应占据首屏空间的功能

这些功能必须保留，但可以只在展开面板或详情中出现：

- 游戏多选及游戏专属属性、稀有度、武器 / 命途 / 特性、地区 / 阵营 / 组织筛选。
- 只看收藏和收藏数量。
- 三档显示密度。
- 周起始日。
- 立绘背景、动态效果和主题跟随偏好。
- 角色详情中的收藏、仅看立绘和编辑。

### P2：低频维护和导出功能

这些功能不需要占用 GPT 首屏构图，但必须能从“更多 / 设置”到达：

- 添加 / 编辑角色。
- JSON 导入和导出。
- 全部角色 ICS 导出和单角色 ICS 导出。
- 更新已发布角色数据、同步进度、成功 / 失败状态和最后更新时间。

如果实现时间不足，优先延后 P2 的视觉精修，而不是删掉 P0 的日期语义或角色详情。P2 的第一版可以使用朴素但清晰的表单和状态提示。

### 取舍顺序

当一个功能会破坏 GPT 视觉时，按下面顺序处理：

1. 先移入统一展开面板。
2. 再缩短文案、改成图标 + 可访问名称或状态摘要。
3. 再把低频操作放进详情或设置。
4. 最后才讨论是否延后功能。

不要首先牺牲月视图、日期模式、搜索、筛选和角色详情。不要把“功能存在”理解成“所有控件都必须同时可见”。

## 3. 和现有代码的结合方式

### 保留为业务层的部分

以下逻辑应尽量原样复用，不要在视觉重绘时重写：

- `useCharacters` 的数据加载、本地存储、手动角色合并、筛选、收藏和同步。
- `src/types` 中的 `Character`、`ViewMode`、`DateMode`、`CalendarDay`。
- `src/utils/calendar.ts` 的日期计算、生日 / 实装回落和月周网格生成。
- `characterData.ts`、`filterUi.ts`、`characterSearch.ts`、`favorites.ts`、`ics.ts`。
- `affiliations*.ts` 和 `useTheme` 的游戏 / 地区 / 阵营数据。
- 现有图片资源、头像缺失回退和立绘比例计算逻辑。

这些是产品行为契约，不是视觉参考。

### 允许重做为展示层的部分

建议重新实现以下展示组件，而不是继续在旧 CSS 上叠加覆盖规则：

- `Header.tsx`：改成 GPT-sol 的品牌标题、日期导航、搜索入口和统一控制入口。
- `FilterSidebar.tsx` / `FilterBottomSheet.tsx`：改成同一套桌面保留轨 / 移动抽屉控制面板。
- `Calendar/DayCell.tsx`、`MonthView.tsx`、`WeekView.tsx`：重做日期格和三档头像密度视觉。
- `CharacterModal`：重做为 GPT 的详情 / 大立绘状态。
- `AddCharacterModal.tsx`：保持字段和导入行为，视觉上作为低频面板整合。
- `Hero.tsx`：复用角色挑选、点击和归属数据逻辑；视觉上不要同时保留旧的全屏 Hero 和新的左舞台，否则会出现两个主视觉。

关键结构决策是：GPT 左侧舞台应成为日历工作区的一部分。可以复用 Hero 的数据选择逻辑，但不要把旧 Hero DOM 和新舞台并排叠加。

### 推荐的临时架构

不要一开始直接覆盖旧组件。先新建展示层，例如：

```text
src/components/redesign/
  CalendarWorkspace.tsx
  WorkspaceStage.tsx
  WorkspaceControls.tsx
  WorkspaceFilters.tsx
  WorkspaceMonthGrid.tsx
  WorkspaceDayCell.tsx
  WorkspaceCharacterDetail.tsx
```

由 `App.tsx` 继续负责状态和业务回调，`CalendarWorkspace` 只接收已经整理好的数据和事件。开发期间使用临时 query 或常量切换新旧展示层，例如 `?ui=redesign`；稳定后再移除旧分支。这样可以在新视觉失败时回到旧界面，也不会污染现有业务逻辑。

## 4. 分阶段实现，而不是一次性重写

### 阶段 A：视觉合同和内容样本

交付：一页视觉合同、三档头像密度样本、桌面和移动静态基准图。

必须明确：

- 页面尺寸、左右比例、网格最小宽度和行高。
- 背景、文字、边框、状态色、游戏 / 地区色的 token。
- 角色图像的裁切规则和无图回退。
- 控件的常驻 / 展开 / 低频分层。

在这一步不写真实业务逻辑。若静态图仍然不好看，停止实现并修改视觉合同。

### 阶段 B：只接入真实日期和角色数据

先实现：

- GPT-sol 外壳。
- 真实月份和 7 列网格。
- 月周切换、翻月、今天、跳转年月。
- 三档头像密度、`+N` 当天名单和角色点击。
- 角色详情的静态信息和立绘。

验收重点是“真实数据进入后仍然好看”。不要先接所有设置和导出。

### 阶段 C：接入高频交互

接入：

- 搜索和搜索结果键盘操作。
- 游戏筛选、游戏专属筛选、筛选摘要和清除。
- 收藏和只看收藏。
- 生日 / 实装模式。

每完成一个功能，都检查它是否改变了主构图、月格行高或移动端首屏。功能状态应通过摘要、颜色和局部面板表达，而不是永久增加顶栏按钮。

### 阶段 D：接入低频功能和设置

接入：

- 添加 / 编辑角色。
- JSON 导入 / 导出。
- ICS 导出。
- 数据更新、同步状态和最后更新时间。
- 周起始日、显示密度、立绘背景、动态效果、主题跟随。

这些功能统一放进“更多 / 设置”入口。低频面板优先保证字段、错误提示和键盘 / 触摸可用，视觉细节可以晚于主工作区打磨。

### 阶段 E：响应式、可访问性和回归

至少验证：

- 1440×900 桌面中性状态。
- 1440×900 游戏 / 地区筛选状态。
- 1440×900 角色详情状态。
- 390×844 移动月视图。
- 390×844 移动筛选抽屉和详情返回。
- 高密度月份、无事件月份、无头像角色、图片加载失败、非闰年 2 月 29 日。
- `prefers-reduced-motion`、键盘焦点、遮罩关闭和按钮可访问名称。

## 5. 头像密度和现有 displayMode 的兼容

GPT-sol 的三档规则应是日期格的自动布局规则，现有 `displayMode = avatar / card / compact` 不应再直接决定三种完全不同的页面结构。

建议映射：

- `avatar`：标准模式，执行单人肖像 / 2–3 堆叠 / 4+ 小头像规则。
- `card`：信息模式，在头像旁显示短角色名；仍遵守三档上限。
- `compact`：紧凑模式，只保留头像、色点和 `+N`；仍保留当天名单入口。

这样可以保留已有偏好和 localStorage 数据，同时避免用户切换显示模式后破坏 GPT 的网格比例。默认模式应是 `avatar`，低频设置中才切换。

## 6. 每阶段验收标准

### 视觉验收

- 第一眼仍然是角色舞台和月历，不是控制面板。
- 7 列日期可在几秒内扫描。
- 去掉背景光晕和颜色后，日期、今天、选中和事件密度仍可理解。
- 高密度月份没有溢出、跳动或不可点击的 `+N`。
- 移动端不是桌面端缩小，也不依赖横向滚动。

### 功能验收

- 旧功能路径仍可到达，或在文档中明确新的入口。
- 生日 / 实装语义没有被视觉层混淆。
- 筛选不会残留旧游戏状态或显示错误数据。
- 搜索结果不受当前日历筛选意外限制。
- 角色详情、收藏、编辑和导出行为正常。
- 同步失败、无有效 ICS 事件和图片加载失败都有明确反馈。

### 工程验收

- 每个阶段完成后 `npm run build` 通过。
- 不改动业务数据格式和 localStorage key，除非有迁移说明。
- 不把大型立绘重复加载到每个日期格。
- 动画可关闭，图片有 `loading="lazy"` 或等价策略。
- 新旧展示层可在开发期间切换，直到视觉合同冻结。

## 7. 最终决策规则

当视觉和功能发生冲突时，按以下顺序判断：

1. 核心日历任务是否仍然可完成？
2. 角色和日期是否仍然有清晰层级？
3. 功能是否可以通过统一入口保留，而不必常驻？
4. 是否只是低频功能的视觉精修不足？

只有当一个功能同时破坏核心任务、无法被面板收纳、且使用频率很低时，才考虑延后。延后必须记录为待办，不应默默删除。
